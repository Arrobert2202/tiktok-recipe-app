Reconciled 19 August 2026; see `docs/MIGRATION-RECONCILIATION.md` for the
full story, what was verified on a Neon branch, and the exact statements
still owed to production. Original finding kept below for context.

`db/migrations/0000_sudden_shadowcat.sql` predates a significant amount of what is now in `db/schema.ts`: the Better-Auth tables, `users.credits`, `extraction_jobs.credit_refunded`, and `recipes.tips_and_tricks`, among others. The live database was evidently moved forward with ad-hoc `drizzle-kit push` rather than generated migrations.

Consequences:

- `drizzle-kit generate` no longer produces a clean incremental diff — it tries to recreate objects that already exist live.
- `drizzle-kit migrate` is therefore unusable, which also means there is no safe automated migration step for deployment.
- Step 3 is a structural change to `recipes`, `recipe_cache`, and `extraction_jobs`. Attempting it on top of a broken migration history risks either a failed deploy or silent data loss.

This must be reconciled before step 3 begins, on a Neon branch rather than production.

## 1. Architectural Overview

A micro-SaaS that turns a TikTok cooking video URL into a structured recipe (ingredients, ordered steps, tips), saveable to a personal cookbook, shareable via SEO/OG-optimised public pages, with a credit-based free tier and a creator opt-out mechanism.

### Stack

| Layer | Choice |
|---|---|
| Framework | Next.js 16, App Router (RSC + Server Actions; almost no REST layer) |
| Database | Neon Postgres via Drizzle ORM |
| Auth | Better-Auth, Google OAuth only |
| Background jobs | Trigger.dev v3 |
| LLM | OpenAI `gpt-4o-mini` via Vercel AI SDK `generateObject` |
| ASR | OpenAI `whisper-1` |
| Media | yt-dlp + ffmpeg, baked into the Trigger worker image |
| Styling | Tailwind v4 |
| Tests | Vitest + fast-check (property-based) |

### Primary flow

```
URL
 └─> actions/extraction.ts
      ├─ validate format + length
      ├─ canonicalize (follows redirects for vm./t/ short links)
      ├─ creator opt-out check
      ├─ recipe_cache lookup       → hit: return immediately
      ├─ in-flight job dedupe      → hit: return existing job id
      ├─ credit check + upfront charge
      └─ enqueue Trigger.dev task
           └─> trigger/extraction-job.ts
                ├─ oEmbed caption fetch
                ├─ yt-dlp audio extract → Whisper transcript
                ├─ LLM "data fusion" parse (caption + transcript)
                ├─ insert recipes row
                ├─ write recipe_cache
                └─ mark job complete  (on failure: refund credit, once)
 └─> client polls /api/extraction/status/[jobId]
      └─> redirect to /r/[slug]
```

### Three entry paths, not one

| Path | Trigger | Cost model | Sync? |
|---|---|---|---|
| `submitAnonymousUrl` | Logged-out landing page | 1 free per hashed IP / 24h | Sync, caption only |
| `submitTikTokUrl` | Signed-in, URL only | Credit charged upfront, refunded on failure | Async via Trigger.dev |
| `submitWithDataFusion` | Signed-in, after a video upload | Credit charged on success | Sync |

This divergence is the single biggest source of the correctness bugs listed in §3.

## 2. Current State Assessment

### Genuinely built and coherent

- **Schema + migration** — complete, sensibly indexed, cascades thought through. The `extraction_jobs` cascade comment shows someone hit the account-deletion FK wall and fixed it properly.
- **Auth** — Google OAuth, account linking, 30-day sessions, and a well-reasoned `BETTER_AUTH_SECRET` guard that correctly distinguishes build phase from serving.
- **Extraction happy path** — oEmbed → Whisper → fusion parse works end to end. The credit refund idempotency (conditional `UPDATE ... WHERE credit_refunded = false`, claim reported via `.returning()`) is textbook-correct.
- **Cookbook** — save / remove / tag actions, sorted and searchable queries, optimistic UI.
- **Public share pages** — SSR, `generateMetadata`, `@vercel/og` image, JSON-LD structured data, opt-out gate on `is_public`.
- **Beyond spec** — shopping list with aisle categorisation (~1,000 lines of pure, testable functions, the cleanest module in the repo), Cook Mode with wake-lock, PWA manifest + share target + service worker, output-language selection, recipe card download, GDPR account deletion, privacy and terms pages.
- **Tests** — 12 property tests, 5 integration suites, plus unit tests. Good discipline, heavily mocked at the DB boundary.

### Spec drift

`.kiro/specs/tiktok-recipe-app/tasks.md` marks **17 of 17 tasks complete. It is not accurate.** At least three completed-marked tasks ship as stubs (5.5, 6.1, 13.2). Treat that file as aspirational until it is reconciled.

## 3. Code Quality & Security Audit

### Critical

1. **No version control.** No `.git` anywhere in the project. Every other recommendation is unsafe to act on until this exists. *(Addressed — see §5 step 1.)*

2. **`/api/transcribe` is an uncapped spend endpoint.** Auth-gated, but no credit check, no rate limit, no per-user quota. A signed-in user can POST 25 MB files to Whisper in a loop. Separately it will likely **fail in production anyway**: Vercel serverless functions cap request bodies at roughly 4.5 MB, and the 30 MB `serverActions.bodySizeLimit` in `next.config.ts` does not apply to route handlers.

3. **Creator opt-out is a stub.** `actions/creator.ts` validates inputs and returns `{ success: true }` with a `TODO (task 13.2)`. Nothing ever writes to `creator_opt_outs`. Therefore `isCreatorOptedOut()` queries a permanently empty table, every gate depending on it is a no-op, and `/creators` tells creators they have opted out when they have not. This is the application's entire ethical and legal shield and it is currently decorative. **Highest-consequence finding in this audit.**

4. **Credit check is TOCTOU.** `hasCredits()` and `decrementCredits()` are two separate statements, and the `UPDATE` has no `WHERE credits > 0` clause despite the docstring claiming "Only decrements if credits > 0." Concurrent submissions drive balances negative. The upfront-charge reasoning in the surrounding comment is correct; the implementation does not deliver it.

5. **Shared recipe rows with per-user edit rights.** The `recipes` table has no owner column, and `updateRecipe` authorises anyone holding a cookbook entry. User A's edit rewrites the public `/r/[slug]` page and the copy in every other user's cookbook.

6. **Client-supplied transcript is published under a real creator's name.** `submitWithDataFusion` accepts an arbitrary `transcript` string from the browser, feeds it to the LLM, publishes the result at a public URL attributed to `@handle` with a link to their real profile, and writes it into the global `recipe_cache`. This is cache poisoning plus attributed-content risk, and a direct prompt-injection channel into the parser.

7. **Middleware may lock out signed-in users in production.** `middleware.ts` looks for the cookie `better-auth.session_token`; Better-Auth prefixes cookies with `__Secure-` over HTTPS. Verify against a deployed session. If wrong, `/cookbook`, `/settings`, and `/shopping-list` redirect-loop in production while working perfectly in local development.

8. **Secrets hygiene.** `.env.local` contains no `BETTER_AUTH_SECRET` and no `IP_HASH_SALT`. The latter falls back to a hardcoded public string (`"recipeapp-anon-salt"`) and is not present in `.env.local.example` at all.

### Correctness bugs

- **Cross-user job dedupe produces a permanent 404.** Step 8 of `submitTikTokUrl` returns an in-flight job for the same canonical URL *regardless of owner*; `/api/extraction/status/[jobId]` then rejects the poller as not-the-owner. User B polls forever and never receives a recipe.
- **Cache ignores language and quality tier.** `recipe_cache` is keyed on `canonical_url` alone. A German-language request returns the cached English recipe. Worse, an anonymous caption-only extraction becomes the permanent cached answer, so a paying user who would have received full audio fusion silently gets the thin version.
- **Opt-out cache is per-process.** In-memory with a 5-minute TTL, and `invalidateOptOutCache()` clears only the lambda instance that calls it. On serverless this means up to 5 minutes of inconsistent enforcement across instances.
- **OG route runtime mismatch.** `app/api/og/[slug]/route.tsx` declares `runtime = "edge"` while importing the Neon `Pool` (Node / ws-based). Also serves a fully deterministic image with no cache headers.

### Technical debt

- **Dead extraction ladder.** `runExtractionLadder`, `tryNativeCaptions`, and `tryAsrTranscription` are unreferenced. `native-captions.ts` and `asr.ts` are `return null` placeholders. The real job hardcodes oEmbed → Whisper. Tasks 5.5 and 6.1 are marked complete. `hasRecipeContent` and the serializer's `deserialize` are likewise tested but never called.
- **Three divergent extraction paths** with copy-pasted validate / canonicalize / opt-out / parse blocks and three *different* credit policies. This is where the next several bugs will originate.
- **`searchCookbook` fetches the entire cookbook and filters in JavaScript**, unpaginated. Acknowledged in a comment and acceptable at 500 recipes, but it is a known ceiling.
- **Dynamic `await import()` used mid-function** for `@/lib/credits`, `@/lib/anon-limit`, and `@/lib/recipe-parser` inside server actions. No benefit at this scale; it obscures the dependency graph.
- **Observability is `console.log`.** No error tracker, no request correlation IDs, no per-user OpenAI cost accounting — on a product whose unit economics *are* OpenAI cost.
- **No test touches real SQL.** The DB is fully mocked, so schema and query regressions are invisible to the suite. No e2e tests, no CI.
- **`status` and `current_stage` are bare varchars** with no check constraints, mirroring TypeScript unions that can silently drift.
- **Legal exposure of the mechanism itself.** yt-dlp downloading TikTok audio is squarely against TikTok's Terms of Service, and is a brittle dependency (the `trigger.config.ts` comment shows this is understood). Worth a deliberate, recorded decision rather than a default.

## 4. Missing Pieces for a Production-Ready MVP

| Area | Gap |
|---|---|
| **Payments** | `PaywallModal` lists six Pro features and has no Stripe, no checkout, no webhook, no subscription state. `credits` is the only entitlement column. The monetisation path dead-ends. |
| **Email** | No provider at all. Blocks opt-out verification (which the spec requires), account mail, and failure notifications. `privacy@tiktokrecipe.app` is promised in error copy — confirm that mailbox exists. |
| **Auth parity** | Spec and `tasks.md` promise email/password (8–128 chars); `betterAuth` has no `emailAndPassword` block and `/auth/signup` merely redirects to signin. Implement it or amend the spec. |
| **Rate limiting** | None for authenticated users, on any server action or route handler. |
| **Migrations on deploy** | Migrations are generated but nothing runs `drizzle-kit migrate` as part of deployment. |
| **CI/CD, staging, runbook** | None. No README. |
| **Error boundaries** | `not-found.tsx` exists; there is no `error.tsx` or `global-error.tsx`. |
| **Abuse & moderation** | No report button on share pages, no takedown/DMCA path, no moderation of user-supplied content that gets published publicly. |
| **GDPR** | Deletion exists; data portability/export does not. |
| **Recipe richness** | No servings, prep/cook time, yield, or nutrition — the JSON-LD is thin, and share pages are the growth engine. |
| **Analytics** | The anon → signup → credit-exhaustion → paywall funnel is the entire business and it is unmeasured. |

## 5. Recommended Action Plan

### Step 1 — Version control and a CI floor

`git init`, verify `.env.local` is excluded, scan for the live Neon / OpenAI / Trigger keys before any remote push, then CI on typecheck + vitest + `next build`. Nothing else should be touched first: there is currently no undo.

### Step 2 — Stop the bleeding: money, abuse, and production lockout

- Make the credit charge a single conditional atomic `UPDATE`.
- Gate `/api/transcribe` on credits, and move the upload off the 4.5 MB path (direct-to-storage) or drop the feature.
- Add per-user rate limits.
- Set real `BETTER_AUTH_SECRET` and `IP_HASH_SALT` in the deploy environment and document both.
- Confirm the middleware cookie name against a real HTTPS session. Cheap check, catastrophic if wrong.

### Step 3 — Fix the data model before building more UI

This is the schema work everything else sits on:

- Give `recipes` provenance/ownership, or split immutable "extraction" from per-user "recipe copy".
- Scope edits per-user.
- Key `recipe_cache` on `(canonical_url, language, quality_tier)`.
- Never cache a client-supplied-transcript result globally.
- Fix the cross-user job dedupe while in there.

Deferring this gets materially more expensive as features accumulate on the current shared-recipe assumption.

### Step 4 — Make creator opt-out real

Pick an email provider and implement task 13.2 properly: persist the request, verify by token, flip `is_public`, purge cache entries, and invalidate across instances via a DB timestamp rather than in-process memory. Implement the reversal flow too. The privacy page and creator portal currently make a promise the code does not keep.

### Step 5 — Consolidate, then monetise

Collapse the three extraction paths into one pipeline with one credit policy. Delete or implement the dead ladder and strategy stubs. Reconcile `tasks.md` with reality so it functions as a status document again. Then Stripe, error tracking, and cost-per-extraction logging as the final pre-launch gate.

---

**Sequencing note:** steps 1–2 are a matter of days. Step 3 is the real engineering. Adding any new user-facing feature before step 3 lands is strongly discouraged.
